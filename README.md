# Mini Quest (DQ風ミニ探索ゲーム)

Next.js + TypeScript で作った、1分で遊べる簡単な探索ゲームです。ポップなドット絵風で、村から武器を拾って魔王っぽい敵を倒し、宝箱を開けるまでを遊べます。

手で遊ぶほかに、**LLM が行動計画を立て、人が1手ずつ承認して進める「AI提案モード」** があります。このモードの LLM エージェントが、どれくらい正しく計画できるかを自動で評価しました（[エージェントの評価](#エージェントの評価)）。

## セットアップと起動

```bash
npm install
npm run dev
# http://localhost:3000 にアクセス
```

### OpenAI APIキー設定（AI提案モードを使う場合）

`.env.local` に以下を追加してください。

```text
OPENAI_API_KEY=sk-xxxx
```

## 操作

- モード切替: 左パネルの「手動 / AI提案（承認実行）」で選択
- リセット: 画面右上の「リセット」ボタン

### 手動モード

- 移動: 矢印キー / WASD
- 調べる・話す・戦う: Enter / Space（対象の隣で実行）

### AI提案モード

1. モードを「AI提案」に切り替える（キー操作は無効化される。リセットのみ可）
2. 「AIに提案させる」を押すと、OpenAI Responses API（gpt-5-mini）を1回呼び出し、最大10手の計画と各手の理由が表示される
3. 「実行（承認）次の1手」で、計画の先頭の1手だけを実行する（API は呼ばれない）
4. 続けて承認するか、「却下」で残りの計画を破棄する

提案を取得したときだけ課金されます。右パネル「AIコスト」に、最後の呼び出しと累積のトークン数・推定コスト（USD / 円換算）を表示します。サーバーの console にも同じ値を出力します。

## ルール / 流れ

1. 村からスタート。NPC A/B/C に隣接して調べるとヒントが聞けます。
   - A: 「村の外には敵がいるぞ。」
   - B: 「敵には武器が必要だ。」
   - C: 「武器はこの村の家にある。」
2. 村の「武器の家」に入り、武器タイルに乗る or 隣で調べると武器を取得（取得後は非表示）。
3. 外Aにいる魔王っぽい敵に隣接して調べると戦闘判定。武器なしなら「攻撃が弾かれた！武器が必要だ。」、武器ありなら撃破。
4. 敵を倒すと門を通って外Bへ進める（門の隣で調べる）。倒していないと「敵が通路を塞いでいる。先に倒そう。」と進めない。
5. 外Bの宝箱の隣で調べるとクリア。クリア後は入力が無効（リセットのみ有効）。

## 衝突判定

- プレイヤーは NPC / 敵 / 宝箱 / 壁 / ドア / 門のマスに侵入できません（重なり防止）。
- ドア・門は「隣接して調べる」で出入りします。
- 武器タイルは乗ることができますが、取得後は非表示になります。

## AI提案の仕組み

```text
ゲームの状態 ──要約──▶ LLM（JSON で最大10手の計画）──解析──▶ 人が1手ずつ承認 ──▶ ルールで実行
```

- `app/game/ai.ts`: 状態の要約（今いるマップ、位置、上下左右の隣のマス、会話済みフラグ、直近5件のログ、そのマップの NPC・出入口・武器・敵・宝箱）と、LLM の返答を行動に直す解析。`MOVE` / `INTERACT` 以外の言い方（`WALK`、`direction: "east"` など）も受け付ける
- `app/game/planner.ts`: OpenAI の呼び出し。アプリの API ルート（`app/api/ai/route.ts`）と評価スクリプトの両方から使う
- `app/game/cost.ts`: モデルごとの単価と費用の計算

## エージェントの評価

AI提案モードの計画を、**人が毎回そのまま承認した場合**にどこまで進めるかを、ブラウザなしで自動実行して測りました。

```bash
OPENAI_API_KEY=sk-... npm run eval -- --model gpt-5-mini --prompt v1 --episodes 5
npm run eval -- --report    # results/summary.md を作る
```

- 1回のプレイは、クリアするか、行動が120手（最短の2.4倍）に達するか、LLM の呼び出しが15回に達したら終わり
- 比較の基準として、ゲームの状態空間を幅優先探索して最短手数を求めた（`app/game/oracle.ts`。**最短は50手**）
- 1回ごとの全行動と LLM が書いた理由を `results/runs/*.json` に残している
- `--budget-usd` で費用の上限を決められる

測ったもの:

- **実行できない移動**: 壁や NPC に向かって動こうとして、位置が変わらなかった手
- **何も起きない「調べる」**: 隣に何もない場所で「調べる」を選んだ手
- **計画が最初に崩れる位置**: 1回の計画（最大10手）のうち、上の2つが初めて起きた手の位置

### 結果（2026-10-05、各5回）

プロンプト v1 はアプリのもの。v2 は v1 に座標の向きの説明を足したもの（下の「プロンプトの方向の誤り」）。

| モデル / プロンプト | クリア率 | クリアまでの手数（中央値） | LLM 呼び出し（中央値） | 実行できない移動 | 何も起きない「調べる」 | 計画が最初に崩れる位置（中央値） | 武器を取った | 敵を倒した | 1回あたりの費用 | 1回の応答時間（中央値） |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| gpt-5-mini / v1 | **4/5** | 95 手（最短の1.9倍） | 11 回 | 10% | 8% | 7 手目 | 5/5 | 4/5 | $0.043 | 18.9 秒 |
| gpt-5-mini / v2 | 3/5 | 90 手 | 11 回 | 7% | 13% | 6 手目 | 4/5 | 3/5 | $0.041 | 18.6 秒 |
| gpt-5-nano / v1 | 0/5 | - | 12 回 | 9% | 16% | 6 手目 | 5/5 | 0/5 | $0.039 | 48.6 秒 |
| gpt-5-nano / v2 | 0/5 | - | 13 回 | 15% | 14% | 6 手目 | 5/5 | 1/5 | $0.038 | 50.2 秒 |

評価全体（20回）の API 費用は $0.80 でした。

### 分かったこと

1. **gpt-5-mini は5回中4回クリアしたが、手数は最短の約2倍。** 10手の計画のうち、6〜7手目で壁にぶつかるか、何もない場所を調べ始める。計画を最後まで使えることは少ない
2. **gpt-5-nano は1回もクリアできなかった。** 武器は全回で取れたが、その先に進めなかった。1回あたりの費用は mini とほぼ同じで、応答は2.5倍遅い。出力単価は安いが、推論に使うトークンが多く、このタスクでは安くならない
3. **プロンプトの向きを直しても（v2）、良くならなかった。** 実行できない移動は mini で 10% → 7% と減ったが、クリア率は上がっていない。5回ずつでは、この差は偶然の範囲を出ない

### 失敗の分析

クリアできなかった13回の行動ログ（`results/runs/*.json`）を読んで、3つに分けた。

#### 1. 家から出られない（13回中10回）

最後の60手のうち40手以上を、武器のある家の中で過ごしていた。武器を取ったあと、家の出口（ドア）に隣接して「調べる」ことができず、家の中を往復している。
gpt-5-nano は、宝箱の無い家の中で「宝箱を開ける」と理由を書いて「調べる」をくり返す回もあった。今いるマップに無いものを、あるものとして計画している。

#### 2. 先の結果を決めつけた計画（理由の文中に「想定」「新マップ」などが出る手が10件）

「ドアを抜けて新マップへ移動する想定」「新マップで宝箱へ向かう」のように、まだ見ていないマップでの行動まで、1回の計画に含めている。ドアを抜けると座標が別のマップのものに変わるので、残りの手は意味を失う。
10手をまとめて計画し、途中の結果を見ずに実行する作り（開ループ）の弱点。

#### 3. 一度見た情報を忘れる（1回）

gpt-5-mini / v2 の3回目は、武器を取らずに村を出たあと、外Aで「武器を探す」行動を数十手くり返した。
LLM に渡す状態は「今いるマップ」と「直近5件のログ」だけなので、村を出た時点で、武器が村の家にあるという情報が消える。

### 次に試すこと

- **計画を短くする / 毎手やり直す**: マップが変わったら、計画の残りを捨てて呼び直す。2つ目の失敗に効くはず
- **訪れたマップの情報を記憶として渡す**: 武器・出口・NPC の位置を、マップをまたいで保持する。1つ目と3つ目の失敗に効くはず
- **回数を増やす**: 5回ずつでは差が見えない。同じ条件で20回以上回す

### プロンプトの方向の誤り

v1 のプロンプトは、出力例で `{"type":"MOVE","dx":0,"dy":1,"reason":"北へ進む"}` としているが、このゲームでは `dy:1` は**下（南）** への移動。v2 では例を `dy:-1`（上・北）に直し、座標の向き（x は右、y は下が正）と、`nearby` が `empty` 以外の方向には動けないことを書き足した（`app/game/planner.ts`）。
評価では v1 も残し、アプリが実際に使っているプロンプトのまま測っている。

### この評価の限界

- 各条件5回と少ない。1回で20ポイント動くので、条件どうしの細かい差は言えない
- 「人が毎回そのまま承認する」前提で測っている。実際の使い方のように、人がおかしな手を却下すれば結果は良くなる
- 迷路は1種類（固定）。別の配置で同じ結果になるかは分からない
- LLM の出力は呼ぶたびに変わるので、同じコマンドでも数値は再現しない（行動ログは残している）

## ディレクトリ

- `app/` Next.js App Router エントリ
- `app/components/` ゲーム画面・グリッド・SVGアイコン
- `app/game/` ステート、マップ定義、ルール（移動・インタラクト）、AI の要約・呼び出し・最短解
- `app/api/ai/route.ts` AI提案の API
- `scripts/eval-agent.ts` エージェントの評価スクリプト
- `results/` 評価結果（`summary.md` と、1回ごとの行動ログ `runs/*.json`）
- `tests/` テスト
